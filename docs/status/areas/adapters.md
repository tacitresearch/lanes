- No WebSockets, and no TLS server: TLS is terminated in front, by the load
  balancer or a reverse proxy. The HTTP client speaks HTTP/1.1, plain or over TLS, over IPv4, a
  connection per call, with no proxy (`CONNECT`); a name resolves to its first IPv4 address.
- The client's TLS context, with its trust store, is made for each call (about 3 ms with
  Ubuntu's). Revocation is not checked. OpenSSL fixes reach Lanes with Lean's toolchain. The
  trust store is `SSL_CERT_FILE` when it is set. The C declares the functions of the OpenSSL the
  toolchain links, 4.1.0, and `scripts/tls-declarations.py` checks them against the system's
  headers, 3.0 on Ubuntu 24.04: 4.1's headers are generated from templates by its own build.
- The PostgreSQL client speaks plain TCP to IPv4 addresses (no TLS yet). It has no `COPY`,
  `LISTEN`/`NOTIFY`, binary formats, named statements, cancellation or pool; a message is
  decoded through a list of bytes, so `message_max` (1 MiB by default) also bounds the memory a
  reply takes. Its live tests run only when `LANES_POSTGRES` names a server; CI runs none.
- That a PostgreSQL server behaves like the store model at an isolation level is a premise, tested
  on a few recorded runs, not proved. The model keeps at most `history_max` transactions in its
  serial order while one is open, and a run beyond its bounds is outside it. At read committed,
  `append` is checked for a free key at its answer only.
- Several shards run as several processes joined by TCP (`Lanes.Peers`); there is no router
  between shards in one process any more (D37), so the cores of a machine are used by running a
  process on each. That shards behave as the one system is proved for the semantics, for two
  shards (`Lanes/Runtime/ShardSound.lean`) and for any number (`Lanes/Runtime/ShardsSound.lean`),
  with an actor's shard fixed for the whole run: an actor that moves, or a `Peers.Config.home`
  that is `none`, is outside it. It is not proved for the running program, where it is still
  trusted that the runtimes and the transport implement `System.shards` with links between
  shards no better than `Link.network`.
- A boot actor that stops as it starts does not behave the same on several shards: the shards
  boot one after another, so a message another boot actor sent it may be kept where the one
  system loses it (`Tests/Split.lean`, `fragile`). The theorem assumes it away
  (`System.SteadyBoot`); invariants of actor states proved for every environment are not
  affected.
- The models of external services are not tested against a real service: the adapters for
  them, the S3 client and the AWS integration's SES, run against fakes, and the other recorded runs are written by hand from
  the documentation. Idempotency keys do
  not expire in the model; a real payment service forgets them after 24 hours. Requests other
  than one that makes a thing (retrieve, list, cancel, refund) are not modelled.
- The S3 client sends and receives whole bodies, in memory, within the HTTP client's
  `maxResponseBytes`; videos go between the browser and S3 through presigned links. Credentials
  come from the environment, are given, or are read at each call from a source (`SigV4.Source`),
  such as the AWS integration's. It has not
  been run against AWS, MinIO or LocalStack, nor over TLS in a test; the XML reader, scoped to
  S3's answers, is not yet tested against Go's. No multipart upload or conditional write.
- The AWS integration has not run against AWS: the metadata service, a container's endpoint and
  SES are fakes written from AWS's documentation as remembered. Credentials come from IMDSv2 or a
  container's endpoint only (no profiles, SSO or STS), over IPv4, and are kept in memory, fetched
  again at each start. SES sends simple messages (no attachments, templates or raw MIME), to
  bare addresses, with no webhooks; it takes no idempotency key, so a send whose answer was lost
  may be sent twice if it is sent again.
- CloudFront's signed URLs and cookies (`Aws.CloudFront`) have not run against CloudFront: they
  are compared with botocore's `CloudFrontSigner`, and what CloudFront takes is read from AWS's
  SDKs, not its documentation. The cookies have no `Domain`, so they reach CloudFront only when it
  serves the site's own host. Keys are RSA of 2048 bits or P-256, in a PEM that is not encrypted;
  a policy's addresses are IPv4.
- The queue, cache, wall-clock, shared-cache and throttling models have no adapter and no recorded
  run of a real system. The queue takes a delete as done when it is handed over and has no
  five-minute window for FIFO deduplication; the cache's leases are memcached's, which Redis gives
  only through a script; the wall clock's skew is not measured; the throttling model has one caller.

# Changelog

What changed in each release of Lanes. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/) as `docs/RELEASING.md` applies it to 0.x. A pull
request that changes the library, the C, the `lanes` command or the app template adds a line
under Unreleased (`CONTRIBUTING.md`).

## [Unreleased]

### Added

- API docs: `docs/api/` builds the reference of `import Lanes` and `import Lanes.Proofs` with doc-gen4 (`lake build +Lanes.Proofs:docs` there, `docs/api/README.md`), and CI builds it as the artifact `api-docs`, with a GitHub Pages deploy that is off until `LANES_DOCS_PAGES` is set (`.github/workflows/docs.yml`). `lanes docstrings` counts the public declarations of `import Lanes` with a docstring, by module, and `--list` names those without one; it fails nothing. Docstrings for the first things a user meets: actors and systems, the semantics' state and events, the scheduler, the checker's model, options and reports, the runtime, the bridge and the gate, routes, services and the journal.
- A scheduler, `Lanes.Schedule` (`Lanes/Behaviours/Schedule/`): work that is due later, held under ids its requester chooses, beside a system (`Schedule.attach`). A job is a call of the outside retried with a capped exponential backoff and a deterministic jitter until it is accepted, gives up (the dead letter, `failed`) or is cancelled; a notice at a time; or a notice every period, to sweep what is over. An id held is one job however often it is scheduled (`already`); beyond `maxJobs` or `maxPayload` a scheduling is refused. Its state is the journal's. Proved: an attempt starts only by its job's timer, once the time it knows has reached the job's run time, and the next only the backoff after a failure (`Schedule.dispatch_due`, `Schedule.retry_waits`); no id is called more than `maxAttempts` times for each scheduling (`Schedule.calls_le_scheduled`); an attempt out ends only with its answer or abandoned at the end of its wait (`Schedule.attempt_ends`); in a fair run in which it does not crash every job ends and its end is handed over (`Schedule.held_ends`). `Schedule.callee` is what a service called may do, for the checker.
- `examples/reminders`: reminders over HTTP, each delivered to a notification service and retried by the scheduler, with a periodic sweep, through a restart on the journal.
- An S3 client (`Lanes.S3`): put, get with a range, head, delete and ListObjectsV2, virtual-hosted or path-style at any endpoint (AWS, MinIO, LocalStack), presigned links for a browser's get and put, credentials from `AWS_*` or given, and `S3.handler` for a system; requests signed with AWS Signature Version 4 (`Lanes.SigV4`), proved to send the canonical path and query that were signed and tested against AWS's test suite and S3's examples; a reader of the XML S3 writes; and a model of an object store with read-after-write and uncertain writes (`ObjectStore.server`, `ObjectStore.read_sent`).
- An AWS integration (`integrations/aws`): a role's credentials from an instance's metadata service (IMDSv2) or a container's endpoint (ECS, EKS Pod Identity), refreshed before they expire by a pure policy proved never to hand out credentials within `skew_ms` of their expiry, to refresh in time when the service answers within the deadline and to bound its backoff (`Aws.Refresh`), model-checked against a model of the metadata service with timeouts; and email through SES API v2's `SendEmail` (`Aws.Ses`), its document proved to carry exactly its recipients and its answers read as the email model's. The deployment's stack takes the instance role by default and can grant `ses:SendEmail` on one identity (`MailIdentity`).
- Sign-in with OAuth 2.0 and OpenID Connect (`Lanes.OAuth`, `Lanes/Web/Auth/OAuth.lean`, `Lanes/Web/IO/SignIn.lean`): the authorization code flow with PKCE, a state used once and bound to its browser and its provider (`OAuth.check_ok`, `OAuth.Used.accepted_once`), ID tokens accepted only for RS256 or ES256 under a key of the provider's JWK Set with every claim checked (`OAuth.IdToken.verify_accepted`), JWK Sets cached and fetched again at most once a minute, and providers of OAuth 2.0 alone known by their user API; done where a request arrives, so no code or token reaches the journal. Presets for Google and GitHub are packages of their own under `integrations/`; `examples/sign-in` signs members in with either and gives them sessions.
- Signatures checked under RSA and P-256 public keys (`PublicKey.verifies`) by the OpenSSL Lean's toolchain ships (`native/verify.c`), with the keys' and signatures' DER written in Lean and a Lean reference for RSA (`Rsa.verifyReference`); JWS in compact form and JWK Sets with an allow-list of algorithms (`Lanes.Jose`).
- HTTPS in the HTTP client: a TLS 1.2 and 1.3 client from the OpenSSL Lean's toolchain ships (`native/tls.c`, `Lanes.Tls`), with the certificate verified against the system's trust store or a file given and the name or address checked, always; `Client.Call` takes a `scheme`, `Call.at` builds a call from an `https://` or `http://` origin, and names are resolved. Nothing new to install.
- Models of external services (`Lanes/Outside/`): `Rpc.outside`, a call answered at most once, `unknown` at its deadline with its effect left open, or never; `Idempotent.server`, idempotency keys, proved to give a request always sent under one key at most one effect in every run the model allows (`Idempotent.at_most_once`); `Events.bounded`, webhooks late, out of order and repeated up to a bound; `Effects`, services that hold things with a lifecycle, and its instances `Payments` (the statuses Stripe documents for a PaymentIntent) and `Email`. `Outside.see`, `Outside.after_induction`, `Outside.after_invariant` and `Outside.after_both` reason about runs a model allows; `System.Emits.outputs` lifts what actors emit to every output of every run.
- `examples/videos`: a video site on S3 and sign-in, Lanes' V1 acceptance application: uploads and playback through presigned links, a `HEAD` before a video is listed, public, unlisted and private videos, likes, comments, a feed and deletes; checked beside the object store's model with two seeded bugs found, and proved: a private video shown only to its owner, each like counted once, a deleted video never shown again, a video shown only after the store confirmed it.
- `examples/payments`: a shop that charges each order through the payment model, checked with the classic bug seeded (a retry without the key charges twice) and proved to charge each order at most once (`Shop.charged_at_most_once`).
- `ServerConfig.ioThreads`: connections owned by dedicated threads, so a connection never changes thread (21–30% more requests a second on the warm machine); and `Runtime.Config.workers`: a batch's actors' steps worked out in parallel, proved equal to the sequential run (`Kernel.runBatchAhead_eq`).
- `Runtime.Config.parallel` (`off`, `on`, `auto`) and `Pace`: with `auto` the shard times each batch and runs the next on its own thread or on Lean's task pool, whichever has been faster, and never puts steps cheaper than 2 µs on the pool; whatever it chooses, the batch is the same (`Batch.run_spread`). `Runtime.batches` counts the batches run each way, and `bench/Auto.lean` measures the three modes.
- `Http.Loopback`: an application's front end driven in tests with no socket, through the server's connection, the gate and the system; and `Http.Client.fetch`, one request to a local server for live tests.
- Requests that stream (`ServerConfig.streams`): a body handed to the system in pieces of at most `piece_max` bytes, framed by its length or in chunks, up to `streamBody_max`, and a response in parts the connection pulls one at a time, each piece and pull a request of its own through the gate (`Lanes.Web.Http.Stream`); Server-Sent Events, with heartbeats and `Last-Event-ID` (`Lanes.Web.Http.Sse`, `Response.events`, `Hx.events`, `Client.events`); the client's reader of events proved to read back what a stream writes (`Sse.parse_written`), and a streamed response's bytes proved to be `Response.wireChunked` (`Conn.read_streamed`). `examples/upload` takes uploads of any size; rookery's timeline is a stream of events.
- Metrics, health and an access log for the HTTP server, each off by default (`ServerConfig.ops`): a metrics page in the Prometheus text format, from `Lanes/Lib/Metrics.lean` (counters, gauges and histograms, proved to escape and to keep buckets cumulative); liveness, and readiness that waits for the shard to recover and goes to `503` on `Server.drain`; `X-Request-Id`, taken from a client when well formed or made; and JSON access lines with no query, header or body. None of it enters a system: a journal is the same with it on as off. `Runtime.hasRecovered` and `Runtime.depth` read a shard's start and its inbox.
- `Http.Server.stopOnSignal`, a stop that drops nothing in flight: at SIGTERM or SIGINT readiness answers `503`, the requests the shard has taken are answered for at most a deadline, then the server stops and `main` returns 0; a second signal ends the process at once. The `main` that `lanes new` writes ends in it, and so do those of `examples/bank-web`, `examples/ledger` and `examples/rookery`.
- `OpsConfig.metricsAccess`: the metrics page is answered only to a peer on a loopback address by default (`Http.Ops.route?_metrics`), or also to a request with a bearer token (`.token`), or to every peer (`.anyone`); any other peer is answered `404` at its path however the path is percent-encoded, which a load balancer's rule on the path did not ensure (`/%6Detrics`). Liveness and readiness answer every peer. `Ip.Addr.isLoopback`.
- Migrations: a deploy that changes a state or message type reads the old version's journal and snapshot. `Journal.Store` has a `version`, which its files carry with the name (`Journal.label`; version 0 is the name alone, so every existing journal reads as before), and `upgrades`, each an older version's system, codecs and a `Migration` to the new one. A start replays the old files through the old step functions, migrates the kernel, hands over the old outputs not yet handed over (`Journal.Log.pending`), saves under the new label and begins the journal at that mark (`Journal.Log.migrate`). A `Migration` carries the proof that every state an old actor reaches lands in an inductive invariant of the new one, which then holds of every actor afterwards (`Migration.inv_exec`, `Journal.Upgrade.inv_load`); dying during the migration gives the same kernel at the next start (`Journal.Upgrade.begin_crash`). `examples/migration` shows a deploy that adds a field.
- `lanes_data … from Old := f` declares how a value of a type's previous version becomes one of this (`T.migrate`, an instance of `Migrate`).
- A PostgreSQL client in Lean (`Lanes/Lib/Postgres/`): the frontend/backend protocol 3.0 with trust, cleartext, MD5 and SCRAM-SHA-256 authentication, the extended query protocol with parameters in text, errors and transactions, over plain TCP; messages proved to read back as written, a connection as a pure `Postgres.Conn.step` proved to answer requests in order and never to report a failed transaction committed, and an IO file that only performs. MD5 and PBKDF2-HMAC-SHA-256 in Lean (`Lanes/Lib/Crypto/`).
- A transactional store model (`Lanes/Outside/Store/`) at read committed and serializable, with lost `COMMIT` answers, as an `Outside`, and an adapter that runs it on a PostgreSQL table (`Postgres.Store.handler`).
- `examples/todo-db`: a to-do list in PostgreSQL, where the checker finds the duplicate row that retrying a lost commit makes, and the fix is proved.
- Every request that arrives at a served or fronted system is answered, in a fair run in which the gate does not crash and the link from outside to the gate loses nothing (`Http.served_arrival_answered`, `Http.fronted_arrival_answered`), so a request whose id is used once is answered exactly once; this was model-checked only. It rests on `System.Run.Fair.delivered`: in a fair run a message on a link that loses nothing, to an actor that stays up, is handed to it.
- `System.Implements.history`: every run of a system that implements a service has a sequential history of the service's acts (`Service.Act`, `Service.play`) that produces each output, takes each input after it arrives and respects real-time order, so statements about the service's functions carry to the system's runs. `examples/rookery` uses it for three of its claims (`Rookery.output_secret`, `Rookery.output_read`, `Rookery.deleted_unread`).
- A test kit, `import Lanes.Testing`, which `import Lanes` does not include: a fake S3 that checks every signature as S3 would, a fake identity provider of OpenID Connect and of OAuth 2.0 with a user API (`Testing.OAuth.Fake`, `Testing.OAuth.signIn`), a scripted browser that keeps cookies (`Testing.Browser`), a server of a handler (`Testing.listen`) and readers of a response. The fakes that `Tests/S3.lean` and `Tests/OAuth.lean` held moved there.
- A fair run of a join is a fair run of its right side alone, seen without the messages from outside in flight, under `EnvModel.right` (`System.Run.Fair.right`), so what the right side alone leads to of its actors it leads to in every join (`System.LeadsTo.join_right`); the left side had this already. The boot of the left side is out of the way, since what it sends the right side is from outside. `System.Reachable.right_unwired`: no output that the wiring routes to the left waits in a join.

### Changed

- `S3.exchange` and `S3.handler` read the credentials of each call from a `SigV4.Source` (fixed credentials still coerce to one), so credentials refreshed elsewhere are used as they change; a call with none is not sent and is answered `unknown`.
- The deployment's stack makes no IAM user for the media by default (`MediaUser` is `false`), and `/etc/lanes/app.env` always gives `AWS_REGION`.
- The object store's model (`Lanes.ObjectStore`) has a head, answered `present` only for a key a put may have left an object under (`ObjectStore.held_sent`), and writes granted to someone else, such as a browser's put through a presigned link, which are never answered and may land at any moment or never (`Request.granted`); the S3 client's head is modelled. Its state keeps the objects sent and read as sets and one settled entry a key, so runs that differ only in repeated history reach the same state.
- The application's stack (`infra/app/`) gives the application its media bucket, as `LANES_MEDIA_BUCKET` in `/etc/lanes/app.env`, which `/etc/lanes/secrets.env` may set again; `examples/videos` reads the bucket from it.
- `Auth.Sessions` ends sessions by a `Lifetime`, idle and absolute, judged at the time a request arrived, with no timer: a session is let in only while it is open and not over at that time and at every time a write was told of before (`Sessions.accepts_iff`); each write sweeps what is over; and a session over is never let in again by any run of operations that does not open it anew, even if the clock steps back (`Sessions.Ended.run`). An entry keeps when its session began and was last used (`Auth.Session`, `Sessions.touch`). `start`, `close` and `live` keep their meaning with no time or lifetime given, so `examples/rookery`, `examples/ledger` and `examples/sign-in` behave as before (no expiry by this; rookery's and the ledger's sessions end by their own timers). The encoding of `Auth.Sessions` changes, so a journal of a state that holds them does not read back.
- `OAuth.Identity` has a `name`, a `DisplayName` of at most 64 characters with no control or reordering mark: OpenID Connect's `name` claim, or GitHub's `name` and else its `login`, cleaned (`DisplayName.clean`); it enters the system in the header `x-lanes-identity-name`, which a client's is dropped from. Google's preset asks for the scope `profile` by default. Code that takes an `Identity` apart by position gains a field.
- The HTTP client's `Host` names the port when it is not the scheme's (`Call.authority`), and a call can be sent as `HEAD` (`Call.headOnly`), its answer read without a body (`Response.readHead`).
- `Http.serve`, `serveWith` and `serveFronted` take `arrive`, work a request needs in IO before it is prepared, which may answer it instead; none by default.
- The `main` that `lanes new` writes reads its address from `LANES_HOST` (`127.0.0.1` unless set; `0.0.0.0` behind a load balancer), how long an idle connection is kept from `LANES_IDLE_MS`, and how long a stop drains from `LANES_DRAIN_MS`. The environment rather than flags: the arguments `[port] [journal]` stay as they were, an application's own arguments need not share a parser with these, and a systemd unit or a container sets them without touching the command line, as `infra/app/app-instance.sh` does.
- `Http.Ops.route?` and `Ops.front` take the address of the request's peer.
- The HTTP server runs its connections on four threads of its own by default (`ServerConfig.ioThreads := 4`); `0` keeps the earlier behaviour.
- Actors step in parallel by default where it pays: `Runtime.Config.parallel := .auto`, and `workers := 0`, the machine's hardware threads, is now the most threads; `parallel := .off` or one worker keeps the earlier behaviour. Unless it is off, inputs that arrive together are one turn, at most `min batch snapshotEvery` inputs to a turn, so the journal has one turn for them, which replays the same. `Kernel.plan`, `Kernel.runWaves`, `Journal.turnAll` and `Batch.Config` take a `Kernel.Spread` in place of a number of workers, and `Batch.group` the most inputs to a group.
- Module paths are reorganised by concern: `Lanes.Actors` is split into `Lanes/Core`, `Lanes/Proof`, `Lanes/Runtime`, `Lanes/Durable`, `Lanes/Net` and `Lanes/Outside`, HTTP, HTML and authentication are under `Lanes/Web`, the standard library under `Lanes/Lib`, and each area's IO in an `IO/` directory; `import Lanes` leaves out the framework's soundness theorems, which a proof imports with `import Lanes.Proofs` (or `Lanes.Semantics`); `Examples/` and `systems/` are one `examples/` directory of Lake packages, `examples/counter` being what `lanes new` writes.
- `Journal.Disk.Holds`, `Journal.Disk.Torn`, `Journal.Kept` and `Journal.memo` take the kernel a history starts from (`start`, boot by default), and their theorems hold for any; `Journal.Kept.saved` says a history without a snapshot starts at boot. `Journal.Store.open` needs `Hashable` of the identities, and a refused journal of an older version without an upgrade is reported with its version.
- `Tests/Fixtures/` keeps the small applications' systems and the two bank theorems the tests carry to shards; the proofs of election, the key-value store and the watchdog are only in their examples.

### Removed

- `Actor.comapMsg`, which nothing used; the `Repr Empty` instance of `Lanes/Core/Inspect.lean`, which Lean has; helper lemmas of the soundness proofs that no proof used.

### Security

- Sign-in keeps nothing on the server for a sign-in begun, so anonymous beginnings can no longer evict other users' sign-ins: the binding cookie holds the state, the provider and the expiry under an HMAC tag by a key drawn at start, the nonce and the PKCE verifier are tags of the state, and the server keeps only the states of accepted callbacks until they expire (`OAuth.Used`, at most `Settings.maxUsed`, which replaces `maxPending`), a full set refusing only tickets older than those it dropped. A state is accepted at most once (`OAuth.Used.accepted_once`) and only from its browser, for its provider, before it expires (`OAuth.check_ok`); a replay is refused as `used`. An identity from a provider of several issuers names the first, so Google's two give one key (`OAuth.Identity.under`).
- The deployment's stack runs no script it has not pinned: `ScriptRef` must be a commit and `ScriptSha256` is required, with no default, and `infra/app/app-instance.sh` refuses to install a script fetched without its hash or with another. The deploy role also trusts only the workflow file `DeployWorkflow` (`deploy.yml` by default) as it is on `DeployBranch`, through the token's `job_workflow_ref`.
- The PostgreSQL client no longer opens a connection that has a password unless the server proves it knows it by SCRAM: `Conn.Config.requireScram`, on by default, refuses an `AuthenticationOk` before SCRAM finishes and a request for MD5 or a cleartext password (`Postgres.Conn.onMessage_requireScram`), and `allowMd5` is off by default.
- `examples/videos`: one member can no longer make the site refuse every new video or comment: a member's videos (`maxOwned`, 100) and comments on one video (`maxCommentsEach`, 10) are bounded far below the site's, and a video's owner may delete anyone's comment on it.
- Every response the HTTP server writes says `X-Content-Type-Options: nosniff`, the connection's own refusals included (`Http.Conn.nosniff`); `Response.noFraming` sends `Content-Security-Policy: frame-ancestors 'none'`, and the pages of `examples/videos` and `examples/rookery` use it.
- `serve` runs `arrive` for at most `ServerConfig.arriving_max` requests at once (64), each on a thread of its own, and answers one more `503`, rather than starting a thread for every request.
- `Http.hostCookie` names a `Secure` cookie `__Host-`; the sign-in's binding cookie and the session cookie of `examples/videos` use it. `examples/videos` writes its key file readable by its user alone, and the deployment's log files are `0640`, readable by the CloudWatch agent's group.
- The S3 client's XML reader replaces references by a loop, in time linear in the text, so a long text from a hostile endpoint no longer exhausts the stack.
- An RSA key is valid for a modulus of 2048 to 8192 bits counted in bits (`PublicKey.valid`): a modulus of 256 bytes with fewer than 2048 bits, which was accepted, is refused.

## [0.1.0] - unreleased

The first public release, a beta. It targets Lean `v4.37.0-rc1` and the CSLib commit pinned in
the Lake file.

### Added

- Actors with pure step functions, systems with an explicit boundary, and effects as data: send, emit, after, cancel, stop.
- One executable semantics of systems, stated as a CSLib labelled transition system, with refinement, specs, fairness and leads-to.
- A model checker with drivers, `always` and `sometimes` properties, refinement checks against a service spec, and seeded random runs with faults; a complete PASS is proved sound.
- A runtime: a proved kernel inside a thin shell, a bounded inbox read in batches, timers as data, and a thread per shard that parks when idle.
- Durability: a journal of what the kernel was asked, replayed at start, with snapshots that cut it; proved to recover the kernel from a file cut at any byte.
- Composition by `System.join`; a system on any number of shards proved to behave as the one system; a transport between processes with its decisions in a pure courier.
- Services as specs, the `Server`, `Once` and `Jobs` behaviours with their proofs, and the standard simulation for proving a service behind actors.
- Proof tools: per-actor invariants lifted to every fault model (`actor_invariant`), ghosts with erasure, monotone invariants, quorums, and where messages come from (`System.Sent`).
- HTTP: a gate joined in front of a system, typed routes proved to print and match alike, a strict request reader, the server's own connection loop on `Std.Net` as a pure `Http.Conn`, and an HTTP client.
- HTML values and a template macro, htmx attributes from routes, forms and cookies with proofs against their specs.
- Authentication: signed tokens, form tokens, sessions, failed-attempt limits and Argon2id password digests.
- Data: `lanes_data` with derived `Codable`, `Enum` and `LawfulBEq`; law-carrying codecs; JSON; Base64; IP addresses and prefixes; civil dates, RFC 3339 and HTTP dates; SHA-256 and HMAC references.
- Bindings to libsodium, `fsync` and a timed thread wait, each beside a Lean reference where one exists.
- Differential tests of the parsers against Go's standard library, with every difference decided.
- The `lanes` command: `new` (an app with a proved counter, a journal and a page), `lint`, `check` and `inventory`.
- A generated inventory giving every public definition its status and evidence, and an axiom gate per area.
- Reference examples: a bank, leader election, a key-value store with front ends, a watchdog.
- Applications built on Lanes: raft-kv (Raft, proved to implement its map, acting once per command), ledger (proved against its timed spec) and rookery (a message board with a JSON API).
- macOS support: libsodium found through pkg-config (Homebrew on Apple silicon included), and a macOS CI job.
- CI with one required check, a merge queue, a mutation gate for trusted code, and a benchmark workflow on a warm runner machine.

### Changed

- The HTTP server reads and writes HTTP itself; `Std.Http` is no longer imported.
- `serve` runs one gate joined in front of the system; the separate gated server is gone.
- The in-process router between shards is removed: shards in one process are one system.
- A spec names its inputs and outputs, and time passes in it as deadlines.
- A deadline may pass where a message is served.
- Actors at rest are released and started again by the kernel, with its theorems up to those starts.
- `Driver.deliver` takes the receiver and the message.
- A JSON object with a repeated key keeps the last value.

### Fixed

- Findings of five code reviews in the runtime, the shell, the HTTP adapter, routes, lint and the checker.
- The kernel's `fire` and the agenda of pending timers.
- The HTTP server and the shard no longer wake on every task, which burned a core while idle.
- Tests that could hang (the wire test's stop, raft-kv's process test) fail in bounded time.

### Security

- The request reader follows a strict profile: the shapes used for request smuggling are refused and every refusal closes the connection.
- URL attributes are rendered through `Html.safeUrl`, so a `javascript:` link cannot be written.
- A request is prepared before it is journalled, so a password or a cookie need never reach the disk.
- Secret comparisons, hashes and random bytes come from libsodium rather than Lean code whose timing is not controlled.
- A journal that is not the one expected, or is damaged other than by a cut, is refused and never repaired.
- CI runs pull requests from forks on GitHub's runners only, and the runner machine's role trusts this repository by its ids.
